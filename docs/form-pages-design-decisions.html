A non-exhaustive overview of the current form pages in the Old UI and the technical constraints they carry.

Form surfaces

  • Full pages
    • Add form: multiple sections, each in its own container; an "Add [Entity]" header, sometimes with a stepper, a type-selection step, or a right pane such as a résumé editor.
    • Edit tab: accessed from the record header; multiple sections, each in its own container.
  • Slideouts (e.g. Add Note): the form fills the slideout width, no container.
  • Modals: the form fills the modal width, no container.

Configurable by the customer

These are set by the customer, not the designer:

  • Field order within a form.
  • Field grouping — which fields are combined into a section (novo-fieldset).
  • Section titles — the wording, or whether a section is titled at all.
  • Section header presence — a section may render with no header.
  • Which fields are required.
The layout must read as intentional under any configuration — arbitrary groupings, any or no section titles, and both header and header-less states. Grouping comes from the container (a carved common region) and the field labels, not from section titles, which may be absent. (Guideline #4; Gestalt — common region.)

System-driven constraints

  • Full-page label alignment is technically constrained. Developers have flagged that moving full-page forms to top-aligned labels will be difficult, since top-aligned labels are the modern single-column default.
  • Slideouts always use top-aligned (vertical) labels. Their narrow width makes labels-beside impractical, so this is fixed by the surface.
  • Modals are a mixed state today (Old UI): some use top-aligned labels, some labels-beside. Label layout in a modal can be decided situationally, based on the modal's usage and width.
  • Footer is always at the bottom across every surface.
  • Container behavior differs by surface. On full pages each section sits in its own container; in slideouts and modals the form fills the surface width within the interior padding, with no per-section container.

Amplify (Bullhorn's AI suite)

Amplify introduces platform-level UI that lays claim to the right side of the screen, which the form layout has to accommodate:

  • Universal chat panel. Can open on the right of any screen; it pushes page content inward and narrows the usable width. The form must reflow to the narrower measure — single column, field cap intact — rather than break.
  • AI-assisted form filling. Adds AI controls to the right side of the form page.
The right pane area is frequently absorbed by Amplify — the chat panel or AI-assist controls. A dedicated context rail cannot assume that space is free, so it is deferred to a later consideration.

These 24 rules translate the design principles, competitive UI research, the Chloe Davis (Sr. Technical Recruiter) persona, and interface heuristics (Nielsen/Molich, Wroblewski, Bringhurst, Gestalt, WCAG 2.2 AA) into concrete form guidance. See the full design guidelines in the appendix for each rule's detail and sources.

Visual design & styling
  • 1. Single column by default. One top-to-bottom path; pair fields on a row only when short and semantically linked.
  • 2. Cap the field, not the card. Cap the field at ~560px (~66–72 characters); size shorter fields to content; size the card to its content and left-anchor it rather than letting it fill or center-float. Design for the narrowed width when Amplify claims the right side; the context rail is deferred.
  • 3. Size each input to its content. Match input width to the expected data so width signals type.
  • 4. Make grouping legible through the container, not the title. Sections are customer-controlled; grouping comes from the container and reads even when untitled.
  • 5. Spend whitespace between sections, not between fields. Set between-section spacing to 2–3× the within-section gap.
  • 6. Build depth from carved borders and tonal layering, not shadows. Reserve real elevation for floating elements.
  • 7. Align to one vertical axis. Labels, inputs, and section headers share a left edge.
  • 8. Build error states from icon, text, and border together. Never signal state with color alone.
  • 9. Design every field state. Scope: default (required and optional), hover, focus, active, complete, error, and disabled/read-only — the last a single combined state per the Old UI.
  • 10. Mark required and optional fields explicitly. One convention, applied system-wide, never color or asterisk alone.
  • 11. Style all primary actions identically. One recognizable primary across every form.
Functionality & interaction
  • 12. Never use a placeholder as a label. Keep a persistent visible label; add a format hint where needed.
  • 13. Label fields in recruiter language. Use the terms the user uses, not internal field names.
  • 14. Keep the whole form on one page. One page, sectioned; no multi-step wizard for records.
  • 15. Cut non-essential fields; pre-fill the rest. Only essential fields; pre-fill from parse, owner, date, parent job.
  • 16. Reveal conditional fields in place. Insert revealed fields inline; never reposition content under the cursor.
  • 17. Validate inline on blur. Not per keystroke, not only on submit.
  • 18. Prevent errors at the input. Right input type, constraints, masks, and controlled-vocabulary pickers.
  • 19. On submit failure, summarize and jump to the first error. Jump links, expanded sections, focus moved.
  • 20. Keep a persistent action bar with an explicit primary. Sticky footer; Save / Save & Add Another / Cancel; name the action.
  • 21. Show save state and protect against data loss. Indicate saved / saving / unsaved; warn before discarding input.
  • 22. Keyboard-complete, mouse-optional. Logical tab order, type-ahead lookups, Enter to save, Esc to cancel.
Implementation
  • 23. Ship every rule as a token or component. Never a per-screen decision.
  • 24. Ensure grouping survives assistive contexts. Back visual sections with semantic headings; pair color cues with shape or icon.

Reviewing three first-iteration patterns in the new UI: an add form with a right pane, an add form without one, and an edit tab. Click any screen to enlarge; use the arrows to move between them.

What the patterns do well

  • Sections read as intentional containers. Each is a carved card, tonally distinct from the page — grouping stays legible without relying on the customer-controlled title. (Guideline #4, #6.)
  • Single-column field path. One clear top-to-bottom flow across all three patterns. (Guideline #1.)
  • Persistent visible labels. Every field keeps its label — no placeholder-as-label. (Guideline #12.)
  • Sticky footer with a styled primary. Cancel plus a filled Save stay anchored bottom-right. (Guideline #20 — partial.)
  • Some control types are signaled. Dropdown carets and lookup magnifiers appear on several fields. (Guideline #3 — partial.)
  • The right-pane pattern is well-formed. In the add-with-pane pattern the card hugs its fields and left-anchors, with the pane beside it and no dead interior space. (Guideline #2, #6.)

Where the patterns diverge from the guidelines

  • Right-aligned, uppercase labels in a narrow column. They wrap to two lines and drift from short-label inputs, reading as dated. (Guideline #7, #13.)
  • Inputs are one uniform full width regardless of content, so width no longer signals data type. (Guideline #3.)
  • Required marking is color-only (a red dot), failing color-blind and screen-reader users. (Guideline #10, #24.)
  • Some constrained controls render as bare boxes, giving no hint whether they are pickers or free text. (Guideline #3.)
  • Input border contrast looks low. Verify it clears the 3:1 non-text minimum; a prior measure was ~2.6:1. (Guideline #8.)
  • The footer says a generic "Save" and lacks "Save & Add Another." (Guideline #20.)

Pattern-specific observations

  • Add page with a right pane. Best-behaved layout of the three: card sized to its fields, left-anchored, with a functional pane beside it (an interactive editor), not a context rail. Establishes the right-pane-as-tool pattern. (Guideline #2.)
  • Add page with no right pane. The form floats in a wide empty gutter rather than left-anchoring — the space beside it has no job. That right area is where Amplify (chat panel or AI-assist controls) will often sit; absent those, it falls to honest margin, with a context rail as a later option. (Guideline #2.)
  • Edit tab with no right pane. The card floats centered and indented past the header's left edge, sharing no vertical axis with the header above it — the concrete "misaligned" case. Its wide inputs hold read-back values in ~590px+ boxes, exactly the line length the field cap governs. Correctly carries no right pane, since record context already sits in the header and sibling tabs. (Guideline #2, #3, #7.)

Field width and card behavior

  • Cap the field at ~560px, not the card. The spec is ~66–72 characters (Bringhurst's 45–75 measure, under the WCAG 1.4.8 80-char ceiling); 560px is that target at Novo's input type — confirm against the actual token. Applies to full-column fields and text areas; shorter fields size to content. This caps both filled-value line length and wrapping helper copy. (Guideline #2, #3.)
  • Size the card to its content; do not let it fill the width. A card whose fields occupy only part of its width reads as unfinished and loosens grouping. (Rams #4, #10; Gestalt — common region.)
  • Left-anchor the card to a shared vertical axis with the page/record header, rather than center-floating it. (Gestalt — continuity; Nielsen #4; Guideline #7.)
Move leftover horizontal space outside the card — into the right pane or honest page margin. Leave leftover width as empty card interior, or stretch the card to swallow it.

Expand right pane functionality

  • Treat the right pane as shared, Amplify-first space. It is frequently claimed by Amplify — the universal chat panel that narrows the page, or AI-assisted form-fill controls docked to the right — or by a functional tool the form requires (the résumé editor, the Add Note editor). Design the form to reflow to the narrowed width these create: single column, field cap intact. (Guideline #2.)
  • A functional tool adapts to the surface. Where there is no room for a right pane, the tool lives inline in the form column; at full size it becomes the right pane. Example: the Add Note editor is inline in the slideout (no right pane) and becomes the right pane in the full-page version. (Guideline #2.)
  • Defer the context rail. A read-only context rail (related records, recent activity, submission status) is worth doing for scenarios where a functional right pane is not required — it puts otherwise-empty width to work and keeps context visible without leaving the form. But because Amplify and functional tools so often absorb the right area, it is deferred to a later consideration, and the form must never depend on it. (Guideline #2; Nielsen — recognition over recall.)

Labels (best-in-class left-aligned)

  • Keep labels beside inputs on full pages (accepting the dev constraint on top-aligned), but make the treatment excellent: left-align the label text, sentence case, not uppercase, on a shared axis with the section header. (Guideline #7, #13.)
  • Left-align over right-align because a consistent left edge keeps every label anchored to its input and lets the eye scan the column in one straight line. (Gestalt — proximity, continuity.)
  • Label orientation follows the surface. Full pages use labels beside inputs (horizontal). Slideouts always stack labels above (vertical), given their narrow width. Modals are situational — pick horizontal or vertical per the modal's usage and width. (Guideline #2, #7.)
Full pages will still differ from the top-aligned modals and slideouts on label position. We are choosing an excellent left-aligned full-page treatment over unifying label position across surfaces. (Guideline #23; Nielsen #4.)

Inputs, controls, and required marking

  • Size each input to its expected content (short / medium / full-column) so width signals data type. (Guideline #3.)
  • Signal every constrained control's type — no bare boxes for Status, Owner, or Heads Up. (Guideline #3.)
  • Raise input border contrast to ≥3:1 on white. (Guideline #8; WCAG 2.2 AA.)
  • Mark required with a non-color cue paired with any color, surviving color-blindness and screen readers. (Guideline #10, #24.)
  • Name the primary action and add the bulk path: "Save [Entity]" plus "Save & Add Another." (Guideline #20.)

Cross-surface consistency

  • Pick one full-page label treatment and apply it system-wide. The iterations use right-aligned labels; the guidelines call for best-in-class left-aligned. Settle one and ship it as a token/component so every form matches. (Guideline #23; Nielsen #4.)

Why it's an improvement

  • Labels read cleanly. Left-aligned, sentence case, on one axis — the core "looks off" fix (was right-aligned, uppercase). (#7, #13)
  • Cards are anchored. Left-anchored and sized to content, so nothing floats — the edit tab no longer sits centered and indented. (#2, #7)
  • Fields carry meaning. Inputs sized to content, and every field state is now a real component. (#3, #9)
  • Errors are handled. A submit-failure summary plus inline icon-text-border errors. (#8, #19)
  • Right side is intentional. Reserved for Amplify or a functional tool; the Add Note editor adapts to its surface. (#2)

A separate stakeholder exploration of the edit-tab pattern, kept apart from the main analysis. It is useful for the ideas it surfaces, not as a design to adopt as-is.

What it surfaces

  • Top-aligned labels. Labels sit above the input, matching the modern single-column default and the modals/slideouts — a point in its favor and worth weighing against the dev constraint on full pages. (Guideline #7, #13.)
  • A real reaction to the "misaligned" centered card. The motivation was dislike of a centered, floating card — a legitimate concern that the main proposal also addresses.

Why it isn't recommended as-is

  • The card fills the full width while fields cap on the left, leaving a large bounded empty region inside the card. A container not sized to its content reads as unfinished and loosens the grouping. (Rams #4, #10; Gestalt — common region, figure-ground.)
  • It fixes the wrong variable. The centered-card problem is solved by left-anchoring the card to a shared axis and sizing it to its content — not by stretching the card to swallow the empty space. (Gestalt — continuity; Nielsen #4; Guideline #2.)
Carry forward the top-aligned label idea as an option to weigh; do not carry forward the full-width card with left-capped fields. The recommended card behavior is in Proposed changes.

The complete Novo form design guidelines. Each rule states the practice and the principle or source behind it. Mirrors Form_Design_Guidelines_Novo.md.

Visual design & styling

  • 1. Single column by default. One top-to-bottom path; fewer errors, higher completion. Pair fields on one row only when short and semantically linked (City/State, Start/End date, Rate/Rate unit). (IxDF §3, Baymard; Gestalt — proximity.)
  • 2. Cap the field, not the card. Cap the field at ~560px (~66–72 characters), within Bringhurst's 45–75 measure and under the WCAG 1.4.8 80-char ceiling; size shorter fields to content. Size the card to its content and left-anchor it to a shared axis rather than filling the width or center-floating; move leftover width to the right pane or page margin. The right pane is frequently claimed by Amplify (chat panel or AI-assist controls), so design for the narrowed width first — the form stays single-column and keeps the field cap — and treat a context rail as a later consideration only where the right area is free. A functional tool adapts to the surface: inline in the form column where there is no room for a pane, becoming the right pane at full size (e.g. the Add Note editor is inline in the slideout, a right pane in the full-page version). Label orientation follows the surface too — full pages beside inputs (horizontal), slideouts always stacked (vertical), modals situational. (Bringhurst; WCAG 2.2 1.4.8; Gestalt — common region, continuity; Rams #4, #10.)
  • 3. Size each input to its content. Short: postal code, extension. Medium: name, email. Full-column: job title, address. Consistent widths per data type let users learn fields by shape. (Wroblewski; Gestalt — similarity.)
  • 4. Make grouping legible through the container, not the title. Section grouping, titles, and header presence are customer-controlled; grouping must come from the container (a common region) and read even when untitled. Design both header and header-less states to look deliberate. (IxDF §4; Gestalt — common region, closure; Rams #8.)
  • 5. Spend whitespace between sections, not between fields. Tighten within-group rows on the 8px grid; set between-section spacing to 2–3× the within-section gap. The ratio creates the grouping. (IxDF §9; Gestalt — proximity; Linear 8px scale.)
  • 6. Build depth from carved borders and tonal layering, not shadows. Hairline borders and background-tone shifts for sections and inputs; reserve real elevation for floating, temporary elements. Data reads as figure, chrome as ground. (Attio carved-border; Gestalt — figure-ground.)
  • 7. Align to one vertical axis. Labels, inputs, and section headers share a left edge; any break in the axis reads as an exception. (Gestalt — continuity; Nielsen #4.)
  • 8. Build error states from icon, text, and border together. Never signal state with color alone. Contrast: 4.5:1 normal text, 3:1 large text and non-text. (IxDF §10; WCAG 2.2 AA; Gestalt — similarity.)
  • 9. Design every field state. Scope the states to default (required and optional), hover, focus, active, complete, error, and disabled/read-only. Default carries required and optional variants differing only by the requirement indicator. Hover is a field-level interactive state; complete marks a satisfied/validated field, shown with a non-color cue such as a check. Disabled and read-only are one combined state — the Old UI does not distinguish them and there is no scope to change that. Disabled/read-only: reduced-contrast label; avoid flat greyscale fills that read as broken. (Rams #8; craft rule 11; Old UI constraint.)
  • 10. Mark required and optional fields explicitly. Never by color or asterisk alone; pick one convention system-wide and pair any asterisk with a text or programmatic cue that survives color-blindness and screen readers. (IxDF §13; WCAG 2.2 AA; Nielsen #4.)
  • 11. Style all primary actions identically. One identical primary style across every form, recognizable before it is read. (Gestalt — similarity, figure-ground.)

Functionality & interaction

  • 12. Never use a placeholder as a label. Keep a persistent visible label on every field; add a format hint where the format is not obvious (e.g. "MM/DD/YYYY"). (IxDF §13; Nielsen/Molich — recognition over recall.)
  • 13. Label fields in recruiter language. Use the terms the user uses, not internal Bullhorn field names. (UX heuristics H2; Rams #4; Chloe.)
  • 14. Keep the whole form on one page. One page, sectioned; no multi-step wizard for records, so users keep random access to any field. (IxDF §4; Chloe — "every click is a candidate.")
  • 15. Cut non-essential fields; pre-fill the rest. Include only essential fields; pre-fill from parsed résumé, the logged-in user as owner, the current date, and the parent job's client company. (IxDF §1, §12; Chloe — goals.)
  • 16. Reveal conditional fields in place. Insert revealed fields inline within the existing section; never reposition surrounding content under the cursor; animate the reveal as one group and respect prefers-reduced-motion. (IxDF §24; Gestalt — common fate, connectedness.)
  • 17. Validate inline on blur. Validate when focus leaves the field — not per keystroke, not only on submit. (IxDF §11.)
  • 18. Prevent errors at the input. Right input type and constraints; masked or typed formats, min–max limits, and controlled-vocabulary pickers over free text. (UX heuristics H5; IxDF §11–13.)
  • 19. On submit failure, summarize and jump to the first error. List failed fields as jump links, expand their sections, and move focus to the first error. (UX heuristics H9; IxDF §10.)
  • 20. Keep a persistent action bar with an explicit primary. Sticky footer so Save is never a scroll away; hierarchy Save / Save & Add Another / Cancel; name the action ("Save Candidate"), not "Submit." (IxDF §21; Chloe — quantity- and KPI-driven.)
  • 21. Show save state and protect against data loss. Indicate saved / saving / unsaved-changes at all times; warn before any navigation that would discard unsaved input. (UX heuristics H1, H3, H5; Rams #8; Chloe — "black hole" pain.)
  • 22. Keyboard-complete, mouse-optional. Logical tab order; type-ahead on every lookup; Enter to save, Esc to cancel with confirm; no keyboard trap in date pickers; typed date entry always available. (Linear ⌘K; IxDF §16; WCAG 2.2 — 2.1.2.)

Implementation

  • 23. Ship every rule as a token or component. Each rule ships as a semantic token or component variant, never a per-screen decision — consistency holds only when enforced in the system. (Chloe — inconsistent-UI pain; Nielsen #4.)
  • 24. Ensure grouping survives assistive contexts. Visual grouping is invisible to screen readers and color cues collapse under color-blindness; pair every color cue with shape or icon and back visual sections with semantic headings and grouping landmarks. (Gestalt A11y cross-check; WCAG 2.2 AA.)
