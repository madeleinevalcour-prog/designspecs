The problem

  • Amplify’s pages (Chat, Overview, Meetings, Audits) sit in tabs at the top of the Amplify page. The design review called top-tab navigation outdated and a poor fit for the new UI.
  • Adding Scheduled as another tab would make a crowded row longer, and the tabs take a second header row away from the content.
  • Overview is being removed.

What changes

  • The Amplify tab in the bowling alley becomes a split tab. Clicking Amplify opens the Amplify landing page (V1: a new chat; V2: Home). The chevron opens the Amplify menu.
  • The Amplify menu lists New Chat, Scheduled (with a count), then Meetings and Audits. V2 adds Home at the top. Overview is gone.
  • The menu opens 8px to the right of the tab, the same as Menu and Add, and supports arrow keys and Escape.
Same opener, chevron and dropdown card as Menu and Add, so it behaves as people already expect (H4, consistency and standards; Gestalt similarity). One place to move between Amplify pages instead of two (Rams #10, as little design as possible).

The problem

  • Today’s header stacks a title row and a tab row. With navigation moving to the bowling alley, the tab row has nothing left to do.
  • The header didn’t say which chat you were in, or link to chat history.

What changes

  • One row on the existing header surface: the Amplify icon container, then a breadcrumb, “Amplify / [page or chat title]”. “Amplify” links back to the landing page. On the landing page itself the header just reads “Amplify”.
  • On the right: a Chats button that opens and closes the Chats panel, then Close. New Chat moved into the Chats panel and the Amplify menu.

The breadcrumb always shows where you are (H1, visibility of system status). The badge tells you something new arrived without keeping the panel open (Rams #5, unobtrusive). The header is one row instead of two (Rams #10).

The problem

  • The design review called the current chat history sidebar unusable.
  • Scheduled prompts add chats that update on their own. People need to see which ones have new results without opening each.

What changes

  • A full-height right panel, the same height as the bowling alley and the docked chat, on the right slideout elevation (level 3 - right). It’s closed by default.
  • Top: title and collapse, a full-width New Chat button, and search.
  • Scheduled section first: up to 3 scheduled chats, each showing its schedule, a status only when it isn’t active (Paused, Needs attention), and unread runs (blue dot + “1 new”). View All goes to the Scheduled page.
  • History below, grouped Today / Yesterday / Previous 7 days / Older. Each chat is a bordered item: title, a one-line description, the record it’s about, and when it was last active (“4 days ago”).
  • Under 1100px wide, the panel opens over the page instead of pushing it.
Each chat is a bordered item and every item has the same line order, so the list scans quickly (Gestalt common region and similarity). Unread uses a dot plus text, never color alone (Modern UI). Scheduled chats appear once, at the top, not again in history (Rams #10).

The user flow (agreed in design review)

  1. The user schedules a prompt from the prompt library or writes a new one. Premade scheduled prompts will be in the prompt library.
  2. A new, dedicated chat is created for that scheduled prompt.
  3. Each time the prompt runs, its output is added to that same chat.

Setting one up

  • Three ways in: New Scheduled Prompt on the Scheduled page, the “Set up a scheduled prompt” starter card on a new chat, or typing “set up scheduled task” (or similar) in any chat input. Asking for something on a schedule (“every Friday at 4 PM…”) also works.
  • Setup uses the existing clarifying questions pattern as the wizard. Amplify asks “What should I run for you, and when?” and offers common scheduled prompts as options, plus Something else and Skip.

The schedule card

  • Amplify replies with one editable card: Name, Prompt, Repeats, a time window, and a fixed Results line. Nothing runs until the user clicks Schedule.
  • Time windows, not exact times. The card offers “Between 8:00 and 9:00 AM”, and each run arrives inside that hour. This gives engineering a buffer and avoids support tickets over small delays (design review).
  • Results: “Posted to this chat. You’ll get a Teams notification with a link back here.”
  • A fixed access line: runs with your access, data stays in Bullhorn.
  • The same card is used to edit a schedule on the Scheduled page.

Confirmation and the dedicated chat

  • Saving replaces the form with a Scheduled confirmation card: name, schedule and next run, with Edit and View in Scheduled.
  • The chat becomes that prompt’s dedicated chat and moves into the Scheduled section of the Chats panel.
One card for create and edit (H4). Nothing runs without the user scheduling it (H5, error prevention; AI governors: preview before committing). Saying “between 8 and 9” promises only what engineering can deliver (H2, match the real world; Rams #6, honest). Clarifying questions is an existing pattern, so setup needs no new wizard component.

The problem

  • The design review flagged that the output format for scheduled prompts needs work.
  • Every run is added to the same chat, and very long chat histories can cause performance problems (slow loading, browser freezes).
  • People want to act on a result (draft outreach, compare matches) without filling the scheduled chat with tangents.

What changes

  • Each run is an Amplify reply holding one run card. The header shows when the run arrived (e.g. “Today, 8:12 AM”) and a “Scheduled run” label. Every card in the chat is the same width.
  • Schedule controls in the card header: a kebab menu with Edit schedule and Pause schedule (or Resume schedule when paused). The output area only holds results.
  • Continue in New Chat (fork): from a whole run, or from one record. It opens a new chat titled “Follow-up: [record]”, with the run and the record as context chips, a short summary and suggested follow-ups. The scheduled chat stays short.
  • A run with nothing to report is one line. A run that can’t complete says why and offers recovery (Review Scope, Resume Without Them).

Three output formats to compare

All three are in the prototype; switch between them in the guide panel.

Expandable records. A summary line, then one bordered row per changed record. Rows expand to show detail and actions. Good for a handful of records that each need action.

Digest. Headline numbers in rounded containers, then one left-aligned line per record with a short description and a fork icon. Fastest to scan.

Compact table. Record, change, and Continue per row. The densest, and best when there are many records.

The kebab menu in a run card header, holding the schedule controls.

The concept

  • Inspired by the Town AI agent: a left-aligned greeting with the day, then one sentence on what’s ahead (“You have 3 meetings today and 4 things to act on”).
  • Left: a compact ask box, a To do list built from scheduled runs (checkbox, source line, one action each), and Suggested prompts.
  • Right: Need to know (short updates with one link each) and Today (the day’s meetings).
  • A Customize button is shown but not built.
It answers “what’s on my plate” first (H1), and each item has one clear next step (Rams #2, useful).

Scope

  • One-time runs. AMP-922 says a prompt can run “one time or on a cadence”. The prototype only covers cadences. How should a one-time run be set up and shown?
  • Saved and premade prompts. Which premade scheduled prompts ship in the prompt library, and does scheduling a saved prompt change it?

Teams

  • Configurable or always on? AMP-922 marks Teams delivery as a question (“if their integration is live”). The prototype shows it as a fixed line.
  • One stream vs channels. All outputs go into one Amplify Teams chat, which may get noisy with many scheduled prompts. Andy is checking whether outputs can go to different channels.
  • Read state. Does opening a run from a Teams link mark it read in Amplify?

Scheduling

  • Which time windows are offered, and is one hour the right width?
  • Which time zone applies (user profile, browser, or company)?
  • Is there a limit on scheduled prompts per user, and does a run count against any usage allowance?
  • Which failures can engineering detect and report (e.g. lost access to records), so the Needs attention states are accurate?

Output and history

  • Which output format (A, B or C), or should it depend on the prompt?
  • At what history length do performance problems start, and what does compression look like to the user?

Navigation and naming

  • “Scheduled prompt” vs “scheduled task”: which term do recruiters use? The prototype uses “scheduled prompt” in the UI and accepts both when typed.
  • How many scheduled chats should the Chats panel show before View All? The prototype shows 3; this is a guess to test.
  • Meetings (transcribe) and Audits move into the Amplify menu unchanged. Confirm nothing else on those pages depends on the old tabs.

V2 homepage

  • Is Home configurable (Customize), and which widgets can be added?
  • Where do To do and Need to know items come from beyond scheduled runs (Ace agent activity)?
