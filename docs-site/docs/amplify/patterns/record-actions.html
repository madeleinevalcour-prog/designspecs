Data tables and cards share one selection pattern. The components are Selection (the selection bar and split button), Data table and Cards.

The chat interface patterns win over these mockups. The whole selection bar is hidden when nothing is selected, and the button label is Title case (“Add 5 Contacts”). The component pages follow those rules.

1. Action lives inside the table card, not on the follow-up row

  • The action bar sits inside the table card's border, so the selected records and the action that applies to them share one region.
  • Principles: Gestalt common region and proximity; H4 consistency and standards. Follow-ups send a message; this button writes data.
  • Research doc §1, pattern table: an agentic card with a data table and multiple actions; inline widgets allow up to two primary actions (e.g., Approve, Edit, Download).
  • Research doc §1, assessment: Make confirmation cards the only way chat can write data.
  • Not in research docBulk actions commonly attach to the selected set. This is from product knowledge; verify before citing.

2. Follow-ups stay visible whatever is selected

  • Selection is the table's state, not the conversation's. Follow-ups don't change when checkboxes change.
  • Principles: Amplify Design Reference principle 2 (AI should only add control — never remove it); H3 user control and freedom.
  • Research doc §1, pattern table: suggested follow-ups are Chips under the latest response.
  • Open question, unchanged in the mockup: "Find matches for #1" refers to a row by position, which breaks if rows are deselected or re-sorted. Naming the record would avoid this (H6 recognition rather than recall).

3. Split button, not a single dropdown button

  • The left segment runs the default action. The chevron segment opens the menu. Each part does one thing.
  • Principles: H7 flexibility and efficiency (one click for most users, more options for power users); Rams 4, understandable.
  • The check icon is removed. A checkmark reads as "done" before anything has happened (H1 visibility of system status; Rams 6, honest).
  • Neither the Novo nor the Component Migration library has a split button. This one is composed from the existing Primary Small button. Confirm whether Novo has one.

4. Label states the verb and the count, and updates live

  • "Add 5 contacts" becomes "Add 3 contacts" as rows are deselected. At 0 selected, the button is disabled and reads "Select contacts to add". The bar stays in place so the layout doesn't jump.
  • "5 of 5 selected" sits next to the action so the user can check the scope without counting checkboxes.
  • Principles: H1; H6; Rams 8, thorough (zero/one/many states designed).
  • Research doc §5, assessment: Use an action preview with a specific verb for any write or outbound message… with a button that names the action ("Send 12 emails," "Update 3 submissions").

5. Completion state, with undo

  • After Add, the bar shows "5 contacts added to Bullhorn · View in Bullhorn ↗" with Undo. Added rows change status and lock at the same time as the bar.
  • Principles: H1; H3; Gestalt common fate (rows and bar change together).
  • Research doc §1, pattern table: a confirmation of the completion of the action… in the form of a card.
  • Research doc §1, assessment: Treat navigation-out as a deliberate, labelled action. Use "Open in Bullhorn ↗".

6. Risk-graded menu actions

  • Adding contacts runs in one click with undo. "Add to an Outreach sequence…" opens a preview before anything is sent; the menu meta text says so.
  • Principles: H5 error prevention; Amplify no auto-act without review.
  • Research doc §4: Risk-graded approvals. Low-risk actions (draft a note) need one click. Higher-risk ones (mass Outreach, status changes on Placements) show a risk indicator and a fuller preview.

Companion to the list (table) variant. Same action pattern, same states, adapted for cards that don't share a container.

1. Cards need a shared region; the list bar provides it

  • In the table, the action sits inside the table's border. Cards have no shared border, so the action bar becomes the last item in the list: same shell as the cards (border/default, radius 8, general/level 1) and the same 8px gap.
  • Principles: Gestalt similarity and proximity (the bar reads as part of the list); Gestalt continuity (the select-all checkbox sits in the same column as each card's checkbox).
  • The cards aren't wrapped in an extra outer container. That would put a border inside a border, against the Modern UI clean principle (separation from tonal borders and spacing, not heavy lines).
  • Research doc §1, assessment: Make confirmation cards the only way chat can write data. The action stays attached to the records it writes.

2. Select-all moves into the bar

  • The table has a header checkbox; cards don't. The bar carries select-all plus "3 of 3 selected", so the scope sits next to the action.
  • Principles: H1 visibility of system status; H6 recognition rather than recall; H7 flexibility and efficiency (one click to clear or reselect all).

3. Bar is sticky to the bottom of the viewport

  • Cards are about 132px tall each, so five or more push the action off screen. The bar pins to the bottom of the chat viewport while the list is in view, and releases when the list scrolls past.
  • Principles: H1; H6. The action stays visible without the user scrolling back.
  • Not in research docSticky bulk-action bars are common in list views. From product knowledge; verify before citing.

4. Same split button, label and completion state as the table

  • Same component, label logic ("Add 2 contacts", "Select contacts to add"), menu and Undo. Users who learn it on a table can use it on cards.
  • Principles: H4 consistency and standards; Rams 7, long-lasting (one pattern across artifacts).
  • Research doc §5, assessment: name the action with a specific verb ("Send 12 emails," "Update 3 submissions"). Research doc §1: a confirmation of the completion of the action… in the form of a card.

5. Completion shows on each card

  • After Add, each added card switches its "Strong Match" chip to "Added to Bullhorn", tints to background/subtle and locks its checkbox. The bar changes at the same moment.
  • Principles: Gestalt common fate; H1. The change is carried by text and the locked checkbox, not by color alone (Modern UI: never signal state with color alone).

6. Follow-ups and response controls are unchanged

  • Same reasoning as the table variant: selection is the list's state, not the conversation's.
  • Amplify Design Reference principle 2: AI should only add control — never remove it. Research doc §1: follow-ups are Chips under the latest response.

Assumptions and known gaps

  • FixedThe Figma copy said "Here are 5 Verizon contacts", with verizon.com emails, while the title said "3 new Comcast contacts". The mockup uses 3 Comcast contacts throughout, including the prompt and emails. Correct this if the source data differs.
  • Flag"Strong Match" uses the success (green) chip. Modern UI reserves success for completion, not ranking. It's left as-is because it's out of scope. "Added to Bullhorn" doesn't use green either, so the two don't compete.
  • InferredThe "Added to Bullhorn" chip uses background/hover with a link-blue border. The file has no "added" or "informational" chip variant.
  • ApproximatedThe Amplify Gradient border uses the exact Figma stops. The angle is approximated as 270° (green left, blue right) from the screenshot, because the Figma gradient transform doesn't map 1:1 to CSS.
  • IllustrativeThe menu items are placeholders, same as the table variant.
  • PrototypeSticky behaviour depends on the chat scroll container. In this standalone page it pins to the browser window.
  • FontInter is not bundled; the preview falls back to system sans.
