Design rationale

Design rationale: adding Prospect contacts from chat

Builds on amplify-chat-record-actions-cards.html. Changes: an inline confirm step, generic activity copy, possible-match handling, no undo, and a record preview.

1. Cost is mentioned once, at the reveal, in generic terms

  • Cost is mentioned in one place: the confirmation, which states "Reveals email and phone" and "Uses Digital Worker Activities". The selection bar stays free of cost copy. No amounts and no balance, because users can't see either.
  • Contact details stay masked (••••••@verizon.com) until the contact is added, the same as the Prospect slideout. The mask shows what the user is paying to reveal.
  • Principles: Rams 6, honest (no invented numbers); Amplify principle 4, set honest expectations; H1, visibility of system status.
  • Research doc §5: ask … only when the answer changes the result or the action is costly.

2. Inline confirm step, because the action can't be undone

  • Add expands the action bar into a confirmation in the same place. It's not a modal, so the records the user is confirming stay in view.
  • It lists what will happen: records created, details revealed, Activities used, can't be undone. The primary button repeats the verb and count ("Add 2 contacts").
  • The selection locks while the confirmation is open, so the scope the user confirms is the scope that runs. Cancel unlocks it and keeps the selection.
  • Principles: H5, error prevention; H3, user control and freedom (Cancel is the exit, since there's no undo); Gestalt common region (the confirmation stays attached to its records); Amplify "no auto-act without review".
  • Research doc §1/§5: an approval dialog shows a preview … and a button labeled with the specific action. Assessment: Make confirmation cards the only way chat can write data.

3. Notify or block only at the edge of the balance

  • Uses last activities: a warning alert inside the confirmation. The user can still proceed.
  • Not enough activities: an error alert. The primary button is disabled and says why, and the alert says who can fix it (your Amplify admin).
  • Both use icon plus text plus the toast warning/negative tokens, never color alone.
  • Principles: H9, help users recognize, diagnose and recover from errors; Amplify principle 8, be honest about limitations; Rams 8, thorough (the edge states are designed).

4. Possible matches reuse the Prospect pattern

  • Adapted from the Prospect slideout's "Matching Contact Records": an info line ("Prospect found 1 possible matching contact in Bullhorn"), a compact record with company, email and status, and "Link contact".
  • The card is unselected by default and carries a "Possible match" warning chip. The user can still select it to add as a new contact.
  • "Link contact" is a secondary button. The response keeps one filled primary action, the Add button.
  • Principles: Amplify principle 5, design for the full range of data quality; H5; H4, consistency (same pattern as the existing Prospect UI); Gestalt common region (the match sits inside the card it belongs to).
  • Research doc §5: Resolve records with a picker, never a guess.

5. Completion shows results and routes to the records

  • The bar becomes "2 contacts added to Bullhorn · View all 2 in Bullhorn ↗". There's no Undo.
  • Each added card swaps to "Added to Bullhorn", shows the revealed email and phone, and locks its checkbox. The bar and the cards change together.
  • The name opens a preview in the chat, so the user stays in context. "Open in Bullhorn ↗" is the separate, labelled way out.
  • Principles: Gestalt common fate; H1; Amplify "keep the recruiter inside Bullhorn"; research doc §1, Treat navigation-out as a deliberate, labelled action.

6. Confirm placement: inline vs. overlay above the input

  • Inline: the confirmation replaces the action bar, inside the response.
  • Strength: the confirmation sits right next to the records it affects (Gestalt proximity and common region).
  • Risk: it scrolls with the response, so on long lists the user may need to scroll to reach it.
  • Overlay above the input: uses the same card as clarifying questions (16px radius, Amplify gradient border, dismiss ×).
  • Strength: it reads as "Amplify needs your answer before continuing". It stays visible at the composer, where the user's attention returns.
  • Overlay consistency: the user meets one pattern for both question types (H4, consistency and standards; research doc §5, a single "Clarify card" … and an "Action preview" would cover every pattern).
  • Risk: the confirmation is further from its records. To compensate, the action bar shows "Review and confirm below" and the selection stays locked (H1; H6).
  • While open, the overlay takes the context bar's place, so the composer area doesn't grow taller and the confirmation sits directly above the input, like clarifying questions. The context bar comes back on Cancel or confirm.
  • Dismiss (×) and Esc both act as Cancel. Nothing runs until the user clicks the named action (H3; Amplify "no auto-act without review").
  • Recommendation to test: use the overlay when the list is taller than the viewport, otherwise inline. Or use the overlay everywhere to match clarifying questions. This needs user testing; I haven't validated either.

Assumptions and open questions

  • AssumptionAdding a Prospect contact always reveals its email and phone (no free path). Adding means create + reveal in one step.
  • AssumptionThe company record is created without revealing extra company data, so the "Company not in Bullhorn" variant carries no separate cost line.
  • OpenDoes "Link contact" reveal data or use Activities? The mockup treats it as free. Confirm with product.
  • OpenWhen the balance is too low, can the system tell whether a smaller selection would fit? If yes, the blocked state could suggest "Try fewer contacts". The mockup doesn't suggest it.
  • OpenIs the balance per user or per organization? The copy says "your organization's".
  • GapPartial failure (for example, one contact's details can't be revealed) is not designed yet. Billing for failed reveals is unknown.
  • GapNo loading spinner component was pulled from Figma. The adding state uses text only.
  • InferredWarning and error alerts use the toast/warning and toast/negative variables. I didn't find an inline alert component in the file.
  • IllustrativeThe names, titles and hiring signals are sample data. The split-button menu items are carried over from the earlier mockup.
  • FontInter is not bundled; the preview falls back to system sans.
