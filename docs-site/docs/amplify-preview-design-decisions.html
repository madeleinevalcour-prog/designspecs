Option 2 is developed but not yet reviewed by a designer.

The problem

  • The candidate preview slideout is an overlay. The docked Amplify chat is part of the page layout. When a preview opens, the slideout sits on top of the chat and the chat can’t be used.
  • This blocks the core Conversational Search workflow: search with Amplify, then preview the results it returns, while still talking to Amplify.
  • Adding Amplify to a workflow shouldn’t take away something the recruiter could already do. Here, opening a preview takes away the chat.

The scenario

  1. A recruiter is on the candidate list with Amplify docked. They asked Amplify to find project managers near Boston, and Amplify applied the filters.
  2. They click the binoculars on a row to look at a candidate in more detail.
  3. The candidate preview opens.

What changes

  • Clicking the binoculars opens the existing slideout, unchanged.
  • If the chat is docked, it turns into the existing pop over (docked-chat state=pop-over) at the same time. It is placed to the left of the slideout, over the list, so the two don’t overlap.
  • A status line under the chat header says why it moved: “Moved to a pop over while the preview is open”.
  • Closing the preview docks the chat again. If the recruiter opened the pop over themselves, it stays a pop over.
  • Clicking Dock to side while the preview is open closes the preview, so the slideout can’t cover the chat again.

Why for Milestone 1

  • No new components. The slideout and both chat states already exist, so the recruiter sees nothing unfamiliar and there is little to build.
  • Unblocks the workflow before the end-of-October deadline.

Trade-offs

  • The chat moves and changes size without the recruiter asking. The conversation they were reading jumps to a new place, which takes control away from them.
  • The list reflows to full width behind the overlays when the chat undocks, then reflows back when the preview closes (everything moves at once, so nothing reads as stable).
  • At 1440px with the bowling alley open, the pop over is about 474px wide. Below roughly 1340px it no longer fits beside the slideout and overlaps it (uncertain: exact breakpoint depends on the final slideout width).
  • The status line explains the move, which helps, but it’s a fix for a surprise the layout creates.

What changes

  • Clicking the binoculars opens the candidate preview as a popover beside the row, using the existing Popover (position=right). Its arrow points at the row’s preview button, which stays in its active state while the popover is open.
  • The content is today’s slideout content, up to 660px wide. The height fits inside the screen.
  • There is no scrim. The docked chat stays where it is and stays fully usable.
  • Clicking another row’s binoculars moves the popover to that row. Previous / Next in the header move through the results.
  • Esc, Close, or a click outside the popover closes it. Clicks in the chat don’t close it.
  • If the list scrolls, the popover follows its row, and hides while the row is out of view.

Why

  • The chat never moves or changes size, so the recruiter stays in control of their workspace.
  • The popover opens next to the row it belongs to and its arrow points at that row, so it’s clear which candidate is showing.
  • It reuses the slideout content, so the preview looks the same as today.
  • Without a scrim, the rest of the page doesn’t look blocked, which matches the fact that the chat stays live.

Trade-offs

  • It covers part of the list: the columns to the right of the preview button. Rows above and below stay partly visible.
  • It will require custom component work: the Popover has to hold the slideout content at up to 660px, stay anchored to its row as the list scrolls, and stay open while the recruiter uses the chat.

What changes

  • The preview opens as a pane between the list and the docked chat, to the left of the chat. The list narrows to make room.
  • The pane is 440px by default and can be resized from 360px up to 660px (today’s slideout width), by dragging or with the arrow keys on its edge.
  • If the list would drop below 480px, the bowling alley collapses (the same behavior the ATS uses on small screens). It opens again when the preview closes.
  • The previewed row is highlighted. Clicking another row’s binoculars swaps the pane content. Previous / Next in the pane header move through the results (“1 of 14”).
  • Open full record (expand) goes to the candidate record page. Esc or Close closes the pane.

Why

  • List, preview and chat are visible together, which matches the task: compare results while asking follow-ups, without having to remember what was in a closed preview.
  • Three fixed columns, each with its own surface, read as three separate tools that work together, in a left-to-right order: results → detail → assistant.
  • The row highlight ties the pane to its row. Previous / Next keeps the recruiter in the flow.
  • Nothing moves without the recruiter asking, except the bowling alley collapse at narrow widths.
  • It is likely easier to implement than Option 2.

Trade-offs

  • The list loses columns at 1440px. Name and Job Title stay visible; the rest scroll horizontally.
  • The pane is narrower than today’s 660px slideout, so the preview content has to work at 360–520px. The prototype stacks label and value in the details card and fits the five workflow tiles in one row.
  • Needs a new pane container and a responsive version of the slideout content.
  • Option 2 is recommended. The chat stays in place and usable, the preview opens next to the row it belongs to, and it reuses the existing Popover and slideout content.
  • Option 1 is the least-effort option if Milestone 1 can’t take any new work. It moves the chat without the recruiter asking.
  • Option 3 is the only option where the list, the preview and the chat are all visible at once. It needs a new pane and a narrow version of the preview content.
This is a design recommendation. The final call, and the Milestone 1 scope, sit with the team.
